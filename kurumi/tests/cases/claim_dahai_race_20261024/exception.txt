用例：claim_dahai_race_20261024
================================

来源
  logs/dump/20261024_152039_exception
  （recorder dump，reason=exception，200 帧）

取帧
  0014490.png – 0014505.png（16 帧，录制原始数据）
  + 0014506.png – 0014510.png（5 张，均为 0014505 的副本，见「为什么补帧」）

起始状态
  states.jsonl 中 fid=14457 的 gamestate 快照，未做任何改动：
  phase=Dahai，current_player=2，last_player=1，last_dahai=1p，
  kawa_index = 3,2,2,3，南四局
  即「玩家 2 已经摸牌、即将打 9s」的那一刻。

场景
  玩家 2 打 9s → 玩家 0 碰 9s → 玩家 0 打 1p。

  游戏侧把「碰」的动画和「打 1p」的动画同时播放，1p 的打牌比碰更早被识别出来。
  在旧实现（tests 分支）里，main 在 Unknown 相位先看到玩家 0 的 dahai(1p)，
  而它记住的 last_player 还停在 2（9s 的打出者），玩家 0 的上家是 3，
  于是轮转校验失败：

      RuntimeError: Unknown 阶段直接识别到打牌，但 last_player(2) 不是
      player(0) 的上家 3，说明有副露未被识别

  碰后出牌权归玩家 0、跳过玩家 3，这本身是正常规则；出问题的是「碰没被识别到」。

refactor（812b371）上的行为
  3 条事件，无异常：

      {"type": "dahai", "actor": 2, "pai": "9s", "tsumogiri": false}
      {"type": "pon",   "consumed": ["9s","9s"], "pai": "9s", "actor": 0, "target": 2}
      {"type": "dahai", "actor": 0, "pai": "1p", "tsumogiri": false}

  碰被正常识别，手番接着交给玩家 0，不再触发轮转校验异常。

为什么补帧
  录制恰好在 0014505 结束。而这一帧里，玩家 0 的 1p 已经在牌河上、碰的牌面也已经
  成型 —— 但 watcher 是靠「与上一帧的差异」检测副露的，需要多一次采样才能把 meld
  报出来，而录制没有给这个采样留时间。

  实测（同样的帧，只改副本数量）：
      原始 16 帧                  → 1 条（只有 dahai 9s，然后就停在 Claim）
      +1 张（14506）              → 2 条（多了 pon）
      +3 张（14506-14508）        → 2 条
      +4 张（14506-14509）        → 3 条（1p 打牌也出来）
      +5 张（14506-14510，本用例）→ 3 条，留一张余量

  所以 0014506–0014510 是**合成数据**，只是给采样更多 tick，画面内容与 14505 完全
  相同。改代码后如果副露识别的采样节奏变了，这个余量可能需要调整。

回归意义
  本用例固定「玩家 2 打 9s → 玩家 0 碰 → 玩家 0 打 1p」这三条事件。
  如果 refactor 的副露识别退化（碰识别不到），事件流会退化成只有 dahai 9s 或再加
  pon，用例即失败；旧实现的轮转校验异常也会让它直接失败。

已知局限
  起始状态取自 14457，而帧从 14490 开始 —— 中间 33 帧的画面变化没有参与回放，
  所以「玩家 2 打 9s」是靠首帧牌河里已有的 9s 反推出来的（kawa_index=2 正好指向它）。
  14506 之后是副本，不是真实录制。refactor 分支的 watcher 对每家独立推进游标，
  行为与 tests 分支不同，这份基线只对 refactor 有意义。
